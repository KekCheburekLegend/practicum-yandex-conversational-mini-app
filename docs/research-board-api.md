# Research Board API

Серверный модуль принимает офлайн-фикстуру или структурированный запрос, хранит версии доски, выдаёт JSON-схему интерфейса и возвращает результат для передачи в чат.

## Локальный запуск

Выполните команды из корня репозитория с Python 3.11+.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python -m uvicorn research_board.app:app --host 127.0.0.1 --port 8000
```

OpenAPI доступна по адресу `http://127.0.0.1:8000/docs`. Тесты запускаются командой `python -m pytest -q tests/test_research_board.py`. Переменная `RESEARCH_BOARD_DB` задаёт путь к файлу SQLite. Родительский каталог должен существовать. Значение по умолчанию — `research-board.db` в текущем каталоге.

## Формат доски

- `claims` хранят текст утверждения, `sources` — заголовок и HTTP(S)-адрес, `evidence` — фрагмент, идентификатор источника и необязательную ссылку на место в источнике (`locator`).
- Направленная связь `links` связывает `from_id` с `to_claim_id`. Для фрагмента доказательства допустимы связи `supports` и `contradicts`. Связь между двумя утверждениями передаётся с `from_type: "claim"` и означает противоречие.
- Связь `contradicts` открыта до решения пользователя. Действие `set_resolution` сохраняет `status: "resolved"` с объяснением в `note`. Статус `open` позволяет повторно открыть противоречие.
- Идентификаторы уникальны внутри каждой коллекции доски, а все ссылки должны указывать на элементы той же доски.
- В выдаче для чата `confirmed_claims` — утверждения с хотя бы одной связью `supports` и без открытых противоречий. Статус `supported` описывает связи, которые пользователь указал на доске. `unsourced_claims` содержит утверждения без привязанного фрагмента, а `unsupported_claims` — без поддерживающего фрагмента. Связь `contradicts` сама по себе не подтверждает утверждение.

## Сессии и действия

Во всех строках ниже используется префикс `/api/research-board/sessions`.

| Запрос | Назначение |
| --- | --- |
| `POST` | Создать сессию из чата. Запрос отправляется на указанный префикс. |
| `GET /{id}` | Прочитать состояние и схему UI. `version` выбирает сохранённую версию, а `board_filter` управляет отображением утверждений. |
| `POST /{id}/actions` | Применить действие или запросить подтверждение. |
| `POST /{id}/confirmations/{confirmation_id}` | Принять явное решение `{"decision":"approve"}` или `{"decision":"reject"}`. |
| `GET /{id}/handoff` | Получить точный state envelope, идентификаторы сессии и диалога и структурированный итог для чата. `version` позволяет запросить конкретную сохранённую версию. |
| `GET /{id}/audit` | Прочитать события для критических операций. |

Для запуска из чата с фикстурой используйте следующий запрос.

```json
{
  "conversation_id": "conversation-1",
  "input": {"kind": "fixture", "fixture": "urban-trees"}
}
```

Для пользовательского ввода передайте `"input":{"kind":"structured","board":{...}}`. Формат доски полностью описан в OpenAPI, а [urban-trees.json](../fixtures/research-board/urban-trees.json) содержит учебный пример. Данные фикстуры вымышленные. Сервер обрабатывает готовые структуры и не обращается к внешним источникам.

В запросе правки передайте ожидаемую версию.

```json
{
  "expected_version": 1,
  "operation": {
    "action": "update_claim",
    "claim": {"id": "night-heat", "text": "Ночный эффект охлаждения нужно проверить."}
  }
}
```

Действия `add_claim` / `update_claim` принимают `claim`, `add_source` / `update_source` — `source`, `add_evidence` / `update_evidence` — `evidence`, `add_link` — `link`, `remove_link` — `link_id`, `set_resolution` — `link_id` и `resolution`. При конфликте версии сервер возвращает `409` без записи новой версии.

`delete_claim` с `claim_id`, `bulk_delete_links` с `link_ids` и `export` возвращают `202` и идентификатор подтверждения. Подтверждение привязано к операции и той версии, на которой её запросили. Для подтверждения после правки нужна новая заявка. Удаление тезиса каскадно удаляет его связи и их решения. Подтверждённый экспорт возвращает снимок в `confirmation.export` без увеличения версии состояния. Журнал сохраняет запрос, отклонение, устаревание, одобрение и исполнение операции.

## Подключение к платформе

Схема UI версии `1.0` использует `component_type`, `props` и `nodes`. Действие фильтра `filter_claims` передаёт выбранное значение из `props.options` в `board_filter`. Формы с `add_*` передают намерение, по которому Chat Shell запрашивает параметры действия. Кнопки `handoff` и `export` используют соответствующие операции API.

SQLite-адаптер даёт локальное сохранение версий, решений и аудита. Общий Runtime, Chat Shell и PostgreSQL из архитектуры потребуют подключения, когда будут доступны в ветке. Описанные HTTP-тесты проверяют контракт входа из чата и возврата в чат на границе сервера. Идентификатор субъекта для аудита берётся из `actor_id` при создании сессии. Аутентификацию и проверку прав должен предоставить общий Runtime перед публикацией API.
