# DevOps: аналитика и план MVP

**Статус:** предложения для команды, не утверждённая конфигурация и не описание существующей инфраструктуры. Цель — сделать локальную разработку, проверку изменений и демонстрацию воспроизводимыми в рамках [архитектуры](architecture.md).

## Окружения

| Окружение | Назначение | Предлагаемый состав |
| --- | --- | --- |
| Local | Разработка и демонстрация без внешних сервисов. | Docker Compose: приложение, PostgreSQL и Redis при подтверждённой необходимости; учебные fixtures. |
| CI | Проверка каждого pull request и изменений в согласованных ветках. | Установка зафиксированных зависимостей, статические проверки и тесты, проверка сборки контейнеров. |
| Demo / staging | Общая демонстрация и приёмка. | Отдельное окружение с тестовыми данными, контролем доступа, сохранением данных и журналами. Хостинг и владелец ещё не выбраны. |

Контейнеры упрощают повторение окружения, но не заменяют тестирование. Публичный адрес сайта и целевая платформа развёртывания пока не предоставлены; до их выбора нельзя обещать публикацию или автоматический деплой.

## Предлагаемый CI/CD поток

1. В pull request запускать проверки стиля и типов согласно выбранным инструментам команды, backend/frontend unit-тесты и проверку сборки. Набор инструментов фиксируется после появления кода.
2. Поднимать изолированные зависимости для интеграционных тестов, применять миграции к чистой тестовой БД и выполнять сценарии registry/router/runtime, state round-trip и confirmation gate.
3. Запускать offline fixtures и evaluator; публиковать понятные результаты, в том числе routing accuracy и schema validity. Порог приёмки — не менее 90% на корпусе минимум 90 запросов.
4. Проверять сборку образов и отсутствие секретов в конфигурации/логах. Версии зависимостей и базовых образов фиксировать и обновлять по решению команды.
5. После утверждения целевого окружения определить, кто и из какой ветки выпускает версию, нужен ли ручной этап допуска, как сохранять миграции и откатывать выпуск. Автоматический деплой пока не предполагается готовым.

Проверки не должны зависеть от платных API или внешней LLM: MVP допускает детерминированный router и локальные fixtures. Защита веток и обязательность проверок настраиваются владельцами репозитория после согласования с командой.

## Конфигурация и хранение

- Параметры подключения и настройки окружения передаются через переменные окружения; пример конфигурации содержит только фиктивные значения. Секреты хранятся в механизме секретов выбранной платформы, не в репозитории или артефактах CI.
- Данные PostgreSQL и загруженные файлы должны переживать перезапуск. Redis не является единственным хранилищем состояния. Место хранения файлов, сроки жизни и очистки требуют решения команды.
- Для demo определить регулярные резервные копии PostgreSQL и файлов, период хранения и проверку восстановления. Миграции выполнять контролируемо; способ отката зависит от конкретной миграции и проверяется заранее.
- В логах достаточно идентификатора запроса, времени, компонента, статуса и безопасной диагностики. Не записывать содержимое файлов, токены и секреты. Доступ к логам и срок их хранения согласовать с командой.
- Проверки готовности и доступности, мониторинг и уведомления проектируются после выбора хостинга и требований к доступности.

## Задачи и результат приёмки

| Задача | Проверяемый результат |
| --- | --- |
| Локальный запуск | Новый участник следует инструкции и получает работающее окружение с fixtures; остановка и повторный запуск не теряют нужные данные. |
| CI | Pull request получает видимый результат проверок и тестов; намеренная ошибка приводит к красному статусу. |
| Миграции | Чистая тестовая БД создаётся миграциями; проверяется обновление с предыдущей поддерживаемой версии. |
| Demo | После выбора хостинга приложение доступно по согласованному URL, доступ к служебным ресурсам ограничен. |
| Восстановление | Из тестовой резервной копии восстанавливаются БД и связанные файлы; результат проверяется сценарием восстановления состояния. |

**Открытые вопросы:** хостинг и домен; владельцы окружения и бюджета; способ хранения файлов; политики доступа, резервного копирования и хранения; обязательные проверки и стратегия релизов; нужна ли Redis в первом срезе; frontend-стек и команды сборки.

## Локальное окружение: Compose

В корне репозитория находится `compose.yaml`: PostgreSQL и Redis запускаются по умолчанию, S3-совместимый RustFS — отдельно через профиль `object-storage`. Это окружение для локальной разработки с учебными данными; backend, миграции, создание S3-бакета и CI здесь не настраиваются.

Нужны запущенный Docker Engine и Docker Compose. Из корня репозитория:

```powershell
Copy-Item .env.example .env
# При необходимости измените порты и локальные пароли в .env.
docker compose config --quiet
docker compose up -d
docker compose ps
```

Состояние `healthy` означает, что проверки доступности PostgreSQL и Redis прошли. Из хост-системы сервисы доступны только на `127.0.0.1`: PostgreSQL — порт `POSTGRES_PORT` (по умолчанию 5432), Redis — `REDIS_PORT` (6379). Из других сервисов того же Compose-проекта используются имена `postgres:5432` и `redis:6379`. Например, URL для будущего backend внутри сети Compose: `postgresql+asyncpg://miniapp:<пароль>@postgres:5432/miniapp` и `redis://redis:6379/0`. Для приложения, запущенного на хосте, вместо имён сервисов используется `127.0.0.1` и порты из `.env`.

Необязательное объектное хранилище:

```powershell
docker compose --profile object-storage up -d
docker compose --profile object-storage ps
```

S3 API доступен на `http://127.0.0.1:9000`, веб-консоль — на `http://127.0.0.1:9001` (или на портах из `.env`). Данные для входа задаются `RUSTFS_ACCESS_KEY` и `RUSTFS_SECRET_KEY`; внутри сети Compose адрес S3 — `http://rustfs:9000`. Хранилище запускается в однодисковом режиме без резервирования, бакет создаётся отдельно.

Для просмотра журналов используйте `docker compose logs -f postgres redis` или `docker compose --profile object-storage logs -f rustfs`. Команда `docker compose --profile object-storage down` останавливает контейнеры, сохраняя именованные тома. **Не добавляйте `--volumes` / `-v`**, если нужно сохранить данные: этот флаг удаляет тома проекта.

`.env.example` содержит только учебные значения, `.env` исключён из Git. Пароль, пользователь и имя базы применяются при первом создании пустого тома PostgreSQL; изменение `.env` не переинициализирует существующую БД. Если порт занят, измените соответствующий порт хоста в `.env` и пересоздайте сервис. Для публичной среды нужны отдельные настройки доступа, секретов, резервного копирования и TLS; текущая конфигурация Redis не требует пароль и предназначена для локальной разработки.
