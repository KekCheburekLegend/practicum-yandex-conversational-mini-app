# Правила работы с репозиторием

Для поддержания чистоты истории коммитов и стабильности проекта все участники придерживаются единого процесса разработки.

### Именование веток

Если изменения затрагивают конкретную часть проекта, добавьте в начало префикс области (`back/` или `front/`):
* `back/<тип-задачи>/<название>` — изменения в бэкенде (например, `back/feat/user-auth`).
* `front/<тип-задачи>/<название>` — изменения во фронтенде (например, `front/fix/login-button`).

Если изменения вносятся в корневую директорию (root) или общие папки проекта, префикс области не указывается:
* `<тип-задачи>/<название>` (например, `docs/readme-update`).

**Типы задач** (краткое описание пишется через дефис на английском языке в нижнем регистре):
* `feat/название-фичи` — новая функциональность.
* `fix/описание-ошибки` — исправление бага.
* `docs/описание` — обновление документации.

### Правила оформления коммитов
* Один коммит должен решать одну конкретную задачу.
* Перед коммитом проверяйте список добавляемых файлов (`git status`), чтобы не загрузить лишнее.
* Сообщения коммитов оформляйте по стандарту:
  * `feat: добавить форму регистрации`
  * `fix: исправить ошибку валидации email`
  * `docs: обновить инструкцию по запуску`

### Требования к Pull Request
* Укажите понятный заголовок и кратко опишите, что было сделано и зачем.
* Убедитесь, что код запускается без ошибок и не ломает существующий функционал.
* Перед слиянием (Merge) устраните все конфликты с `main` и дождитесь прохождения ревью. В ревьюеры назначайте тимлида или другого разработчика, отвечающего за этот же раздел (по согласованию с тимлидом).
* После успешного слияния удалите рабочую ветку.
